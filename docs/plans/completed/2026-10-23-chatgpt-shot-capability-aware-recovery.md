# 2026-10-23-chatgpt-shot-capability-aware-recovery

## Objective

`chatgpt-shot`이 정상 실행뿐 아니라 실패 및 복구 상황에서도 자신의 실행 상태와 한계를 명확하게 전달하고, 에이전트가 사용자에게 불필요한 개입을 요구하거나 예기치 않은 브라우저 실행 및 중복 제출을 발생시키지 않고 안전하게 사용할 수 있도록 개선한다.

실행 환경의 능력과 사용자 권한에 따라 가능한 기능을 제공하되, 사용할 수 없는 기능이나 불확실한 원격 상태를 임의의 복구 행동으로 대체하지 않는 실행 계약을 확립한다.

## Intent

현재 `chatgpt-shot`은 비동기 Job 접수, 원격 Notion 상태 확인, 제출 증거 분류, 로컬 실행 기록 등 신중한 실행 계약을 갖추고 있다.

그러나 외부 에이전트가 이를 사용할 때 다음 문제가 발생할 수 있다.

- 브라우저 지연, 세션 오류, 봇 체크, 인증 만료, Notion 응답 문제 등에서 다음 행동을 안정적으로 선택하기 어렵다.
- `doctor`와 `open`을 일반적인 복구 명령으로 취급하여 원하지 않는 브라우저 실행이나 장시간 대기가 발생할 수 있다.
- 제출 실패 메시지와 실행 기록을 연결하고 기존 Job을 추적하는 과정이 에이전트의 해석에 의존한다.
- 전송이 불확실한 상황에서 재제출 가능 여부와 안전한 복구 방법을 판단하기 어렵다.
- 브라우저, Notion, 로컬 파일, 대화형 사용자 개입 등의 지원 여부가 환경마다 다를 수 있다.
- README의 규칙만으로는 외부 에이전트가 실제로 선택하는 복구 행동을 충분히 통제하기 어렵다.

목표는 모든 실패를 자동 복구하는 것이 아니라, 확인된 사실과 불확실성을 명확하게 드러내고 적절한 복구 또는 사용자 개입으로 연결하는 것이다.

현재의 원격 접수 확인 및 Notion Invocation 권한 경계를 보존하면서 진단과 사용 경험을 개선한다.

## Verification Requirements

**VR1. 정상 실행 계약 보존**

- 정상적인 프롬프트 제출과 원격 Job 조회가 계속 작동해야 한다.
- `submit`의 기존 성공 계약인 접수 확인 후 단일 Job UUID 반환이 보존되어야 한다.
- 접수와 최종 완료가 구별되어야 하며 최종 Result와 Error의 원격 소유권이 유지되어야 한다.
- 기존의 병렬 제출, 브라우저 프로필 공유 제어, 승인된 Job의 브라우저 컨텍스트 정리 계약을 훼손하지 않아야 한다.

**VR2. 예측 가능한 진단 동작**

- 기본 진단은 새로운 브라우저 세션이나 가시적 브라우저 창을 실행하지 않아야 한다.
- 실제 브라우저를 사용하는 진단은 별도의 명시적 요청으로 구별되어야 한다.
- 진단 결과는 확인한 항목, 확인할 수 없는 항목, 실패한 항목을 구별해야 한다.
- 진단을 위한 불필요한 원격 Job 생성, 제출, 설정 변경이 없어야 한다.

**VR3. 사용자 개입 경계**

- 가시적 브라우저 실행은 사용자의 명시적인 개입 경로와 구별되어야 한다.
- 일반적인 실패 처리 또는 비대화형 자동 실행 과정에서 임의로 가시적 브라우저를 열지 않아야 한다.
- 인증, 봇 체크 등 사용자 개입이 필요한 상태에서는 구체적인 이유와 필요한 행동이 전달되어야 한다.
- 로그인 또는 봇 체크를 임의로 자동화하거나 우회하지 않아야 한다.
- 수동 개입을 거절하거나 수행할 수 없는 경우에도 가능한 조회·진단 기능은 유지되어야 한다.

**VR4. 구조화된 실패 및 복구 정보**

- 제출 실패에서 가능한 범위의 로컬 실행 식별자, 오류 코드, 제출 증거, 원격 접수 관찰 결과 및 다음 행동을 일관되게 조회할 수 있어야 한다.
- 로컬 실행 기록과 원격 Job 상태의 출처 및 신뢰 수준이 구별되어야 한다.
- 기존 Job을 찾고 재확인하는 경로가 명확해야 한다.
- 판단 근거가 부족한 상태를 성공, 실패, 미제출 또는 재제출 안전으로 임의 변환하지 않아야 한다.
- 에이전트가 기계적으로 해석할 수 있는 안정적인 결과 형식이 제공되어야 한다.

**VR5. 안전한 재제출 및 복구**

- 미제출이 확인되고 필요한 정리가 완료된 경우에만 자동 재제출 가능성을 인정해야 한다.
- 전송 여부 또는 원격 접수가 불확실한 경우 자동 재제출하지 않아야 한다.
- 이미 접수된 Job은 제출 호출이 오류로 끝났더라도 기존 Job으로 추적할 수 있어야 한다.
- `ADMISSION_TIMEOUT`, `SUBMISSION_UNCERTAIN`, `ADMISSION_CANCELLED`, `BROWSER_CONTEXT_CLOSE_FAILED` 등에서 기존 원격 상태를 임의 변경하거나 중복 작업을 생성하지 않아야 한다.
- 복구 시도가 기존의 진행 중인 제출과 다른 Job의 상태를 훼손하지 않아야 한다.

**VR6. 실행 능력별 사용 가능성**

- 로컬 진단, Notion 조회, 비공개 브라우저 제출, 가시적 브라우저 개입을 각각 구별해야 한다.
- 한 기능을 사용할 수 없더라도 독립적으로 가능한 기능은 사용할 수 있어야 한다.
- 기능 부족, 사용자 권한 부족, 일시적 오류, 상태 불확실성을 서로 다른 이유로 전달해야 한다.
- 사용할 수 없는 기능을 복구하기 위해 임의의 설치, 환경 변경, 브라우저 실행 또는 서비스 중단을 강제하지 않아야 한다.
- 동일한 실행 계약이 CLI와 지원되는 로컬 HTTP 경로에서 일관된 의미를 가져야 한다.

**VR7. 기존 데이터 및 보안 경계 보존**

- Notion Invocation의 원격 소유 State, Result, Error 계약을 유지해야 한다.
- 불확실한 제출의 Invocation을 임의로 삭제하거나 실패 상태로 덮어쓰지 않아야 한다.
- 로컬 진단, 프로필, Service discovery, 인증 정보의 기존 보호 경계를 유지해야 한다.
- 권한이 필요한 외부 효과를 진단이나 복구 명목으로 확대하지 않아야 한다.
- 기존 수동 인증과 승인된 Notion 접근 흐름을 불필요하게 변경하지 않아야 한다.

## Definitions

- **Admission(접수 과정)**: 로컬 제출 요청에서 원격 Invocation의 접수 확인까지의 과정.
- **Delivery(전송 여부)**: 프롬프트가 ChatGPT Web에 전달되었는지에 관한 로컬 증거 기반 분류. `submitted`, `not_submitted`, `uncertain`으로 구별한다.
- **Remote Acceptance(원격 접수)**: Notion Invocation State에서 `in_progress`, `completed`, `failed` 중 하나가 관찰된 것.
- **Terminal State(최종 상태)**: 원격 Invocation의 `completed` 또는 `failed`.
- **Attempt(로컬 실행 시도)**: 제출 요청과 관련된 로컬 실행 기록. 원격 Job lifecycle과 동일하지 않다.
- **Reconciliation(상태 대조)**: 기존 Attempt 및 원격 Job을 조회하여 현재 확인 가능한 결과와 불확실성을 정리하는 것. 새로운 제출을 의미하지 않는다.
- **Passive Diagnosis(비활성 진단)**: 새로운 브라우저 또는 Job을 생성하지 않고 가능한 상태와 기록을 확인하는 진단.
- **Active Diagnosis(능동 진단)**: 실제 브라우저 실행처럼 추가 실행 능력과 명시적 요청이 필요한 진단.
- **Capability(실행 능력)**: 현재 환경에서 특정 기능을 기술적으로 수행할 수 있는지에 관한 조건.
- **Authorization(실행 권한)**: 기술적으로 가능한 행동을 사용자가 허용했는지에 관한 조건.
- **Human Intervention(사용자 개입)**: 인증, 브라우저 확인 또는 수동 승인처럼 사용자의 행동이 필요한 단계.
- **Retry Safety(재제출 안전성)**: 기존 요청이 중복 실행되지 않는다는 근거를 바탕으로 새로운 제출을 시작할 수 있는지에 관한 판단.

## Decisions

### D1. 진단을 실행 효과에 따라 분리한다

기존 `doctor`의 기본 동작을 비활성 진단으로 변경한다.

기본 진단에서는 설정, 기존 Service 상태, 로컬 진단 및 접근 가능한 비파괴적 상태를 확인하되 새로운 브라우저 세션이나 Service를 시작하지 않는다.

실제 브라우저 준비 상태를 확인하는 기능은 `doctor --browser`와 같이 명시적으로 선택할 수 있는 능동 진단으로 제공한다.

능동 진단에서도 시스템에 보이는 Chrome을 열거나 사용자의 인증을 대신 수행하지 않는다.

진단 결과에는 확인한 범위와 생략된 검사를 표시한다. 확인하지 않은 항목을 정상으로 판정하지 않는다.

### D2. 가시적 브라우저 실행에 수동 개입 경계를 둔다

`open`은 사용자가 인증이나 브라우저 확인을 수행하는 명시적인 수동 명령으로 유지한다.

다만 일반적인 비대화형 실행에서는 브라우저를 바로 실행하지 않고 사용자 개입 필요 상태를 반환하도록 한다.

대화형 실행에서는 브라우저 실행의 효과를 알리고 명시적인 확인을 거친다. 단순히 TTY가 존재한다는 사실만으로 사용자 승인까지 확보되었다고 간주하지 않는다.

신뢰할 수 있는 별도 사용자 승인 경로가 지원된다면 동일한 경계를 적용할 수 있지만, 별도의 범용 승인 시스템을 이번 작업의 전제 조건으로 만들지 않는다.

사용자 개입이 불가능한 경우에는 실행을 중단하고 필요한 수동 행동을 안내한다.

### D3. Smoke 검증에서도 예상하지 못한 브라우저 실행을 방지한다

현재 smoke 과정은 인증 실패 시 `open`을 직접 실행할 수 있다.

이를 무인 실행과 사용자 개입이 가능한 실행에서 명확히 구별한다.

- 무인 실행에서는 브라우저를 임의로 열지 않고 명확한 진단 결과를 반환한다.
- 수동 인증이 필요한 경우 사용자가 허용한 경로로 인증할 수 있다.
- 인증 이후에는 기존의 실제 제출·Job 조회 검증을 계속 사용할 수 있다.
- Smoke가 기존 사용자 프로필이나 일반 Service 실행을 침범하지 않는 격리 계약을 유지한다.

### D4. 기존 Attempt를 중심으로 복구 정보를 제공한다

로컬 실행 기록에 기반한 구조화된 복구 조회 기능을 제공한다.

기본 인터페이스는 `chatgpt-shot inspect <uuid>` 형태의 읽기 전용 조회 명령으로 정한다.

해당 명령은 다음 정보를 구별해 제공한다.

- 로컬 Attempt의 식별자와 확인된 실행 단계.
- 제출 여부에 관한 증거.
- 확인된 원격 접수 및 Job 상태.
- 확인하지 못한 항목과 그 이유.
- 재제출 가능 여부에 관한 보수적인 판단.
- 다음에 수행할 수 있는 조회 또는 사용자 개입.

기존 로컬 기록은 Notion이나 브라우저에 접근할 수 없어도 조회 가능해야 한다.

Notion 조회 능력이 있는 경우에는 기존 Job의 원격 상태를 대조할 수 있지만, 원격 조회 불가능을 로컬 제출 실패로 해석하지 않는다.

진단을 위해 새 Job이나 프롬프트를 제출하지 않는다.

### D5. 제출 실패와 Attempt 식별자를 연결한다

로컬 Attempt가 생성된 후의 제출 실패는 가능한 경우 해당 Attempt를 조회할 수 있는 식별자를 제공한다.

CLI에는 기계적으로 해석 가능한 실패 정보 경로를 제공하되, 기존 성공 시 stdout에 UUID 하나만 출력하는 기본 계약을 유지한다.

HTTP 오류 응답도 기존 `{code, message}`의 의미와 호환성을 유지하면서 필요한 상관 식별자와 구조화된 정보를 제공한다.

기존 `attempts` 기록을 중복 저장하는 새로운 진단 이력 시스템은 만들지 않는다.

### D6. 재제출 판단은 증거에 근거한다

자동 재제출 가능 여부는 보수적으로 판단한다.

- 미제출과 필요한 정리가 확인된 경우에만 안전한 재제출로 판단한다.
- 전송 여부가 불확실하면 자동 재제출하지 않는다.
- 전송은 확인되었지만 원격 접수를 관찰하지 못한 경우에도 자동 재제출하지 않는다.
- 원격 접수가 확인된 경우에는 기존 Job을 추적한다.
- 로컬 기록 부족, 네트워크 오류, 취소 또는 시간 초과만으로 미제출을 확정하지 않는다.

재제출을 자동으로 수행하는 범용 복구 명령은 추가하지 않는다. 이번 작업의 복구는 우선 기존 상태를 확인하고 올바른 다음 행동을 결정할 수 있게 만드는 데 집중한다.

### D7. Capability와 Authorization을 구별한다

지원 범위를 다음처럼 독립적으로 다룬다.

| 능력 | 지원 가능한 작업 |
|---|---|
| 로컬 기록 접근 | `attempts`, 로컬 진단 및 복구 정보 확인 |
| Notion 접근 | 기존 원격 Job 및 State 조회 |
| 비공개 브라우저 실행 | 실제 프롬프트 제출 및 능동 브라우저 진단 |
| 가시적 브라우저와 사용자 개입 | 수동 인증 및 브라우저 확인 |

이 능력들은 항상 함께 존재한다고 가정하지 않는다.

또한 기능이 존재한다는 사실이 실행 권한까지 의미하지 않는다.

필요한 능력이 없으면 해당 기능의 제한을 표시하고, 다른 기능이 가능하다면 독립적으로 제공한다.

### D8. 기존 핵심 계약과 범위를 보존한다

다음 영역은 기존 의미를 유지한다.

- Notion Invocation의 생성 및 원격 lifecycle.
- 접수 확인을 기준으로 한 제출 성공 의미.
- 원격 Job의 Result 및 Error 소유권.
- 현재의 제출 증거 분류와 보수적인 정리 정책.
- 병렬 제출과 Notion 요청 조정.
- Browser Broker의 프로필 소유권과 컨텍스트 정리.
- 인증 정보, 브라우저 프로필, 로컬 기록의 접근 보호.
- 기존에 허용된 Notion 승인 보조의 대상 및 권한 범위.

진단과 복구 편의를 위해 이 계약들을 우회하거나 확대하지 않는다.

새로 추가하거나 수정하는 파일, 모듈, 타입, 주요 함수의 이름은 현재 책임을 드러내도록 한다. 이번 변경에만 의미가 있는 이름이나 아직 존재하지 않는 범용 추상화를 기준으로 명명하지 않는다.

### D9. 문서 변경 책임

이 계획에서 바뀐 명령 및 실행 계약은 README와 관련 사용 지침에 반영한다.

별도의 README 개선 계획이 확립한 사용자 중심 정보 구조를 유지하며, 필요하지 않은 전체 문서 재설계는 수행하지 않는다.

## Planned Units

### U1. 진단 및 사용자 개입 경계

기본 진단과 능동 진단을 분리하고, 가시적 브라우저 실행 및 smoke의 사용자 개입 조건을 정리한다.

결과물은 실행 효과가 예측 가능하고 의도치 않은 브라우저 실행을 방지하는 명령 체계다.

### U2. 실행 상태 및 복구 정보

기존 Attempt와 원격 Job을 대조할 수 있는 구조화된 조회 기능을 제공하고 제출 오류와 실행 기록의 연결을 개선한다.

결과물은 에이전트가 추측 없이 실패 상태와 다음 행동을 판단할 수 있는 진단 인터페이스다.

### U3. Capability별 실행 가능성

각 기능이 요구하는 실행 능력과 권한을 명확히 구분하고, 일부 기능이 없는 환경에서도 독립적인 기능을 유지한다.

결과물은 제한된 환경에서 불필요한 복구 시도를 하지 않고 지원 가능한 기능을 계속 이용할 수 있는 실행 동작이다.

## Verification

### V1. 정상 제출 계약 — VR1

실제 CLI를 통해 프롬프트를 제출하고 원격 Notion 접수 상태를 확인한다.

반환 UUID로 기존 Job을 조회해 원격 상태와 연결됨을 확인한다.

접수 전에 성공을 반환하거나 최종 완료까지 불필요하게 대기하면 실패다.

기존 병렬 제출 및 승인 후 브라우저 컨텍스트 정리도 관련 통합 경로에서 확인한다.

### V2. 기본·능동 진단 분리 — VR2

브라우저 및 Service가 시작되지 않은 환경에서 기본 `doctor`를 실행한다.

새 브라우저 세션, 가시적 Chrome, Job이 생성되지 않는지 확인한다.

능동 브라우저 진단을 명시적으로 요청했을 때에만 실제 브라우저 검사가 수행되는지 확인한다.

검사를 생략하거나 실패한 경우 정상으로 잘못 보고하면 실패다.

### V3. 수동 개입 및 브라우저 실행 — VR3

인증 만료, 봇 체크, 수동 프로필 열기, 비대화형 smoke 실행의 대표 상황을 검증한다.

사용자 승인 없이 가시적 브라우저가 실행되지 않아야 한다.

허용된 대화형 경로에서는 정상적으로 수동 인증을 수행할 수 있어야 한다.

개입이 불가능할 때는 필요한 행동과 이유를 보고해야 한다.

### V4. 구조화된 복구 정보 — VR4

다음 상태의 Attempt와 Job을 조회한다.

- 미제출이 확인된 실패.
- 전송이 확인되고 접수되지 않은 상태.
- 전송 여부가 불확실한 상태.
- 원격 접수가 확인된 상태.
- 접수 후 브라우저 컨텍스트 정리에 실패한 상태.
- 로컬 기록만 남아 있고 Notion에 접근할 수 없는 상태.

각각의 식별자, 증거, 원격 관찰 결과, 불확실성, 다음 행동이 일관된 형식으로 제공되어야 한다.

확인하지 못한 상태를 확정적으로 보고하면 실패다.

### V5. 안전한 재제출 — VR5

제출 직전 실패, 전송 이후 시간 초과, 불확실한 전송, 호출 취소, 접수 후 정리 실패를 재현한다.

미제출이 입증되지 않은 상황에서 자동으로 새 제출을 만들지 않아야 한다.

원격 접수된 Job의 State나 Error를 로컬 복구가 임의 변경하지 않아야 한다.

새로 생성된 중복 Invocation이나 훼손된 기존 Job이 발견되면 실패다.

### V6. Capability별 동작 — VR6

다음 환경을 대표적으로 검증한다.

1. 전체 실행 능력을 갖춘 환경.
2. 로컬 진단 기록만 사용할 수 있는 환경.
3. Notion 조회는 가능하지만 브라우저 실행은 불가능한 환경.
4. 브라우저는 실행 가능하지만 인증이 필요한 환경.
5. 대화형 사용자 개입이 없는 자동 실행 환경.
6. 실행 능력은 있지만 개입 권한이 허용되지 않은 환경.

각 환경에서 가능한 기능이 동작하고, 불가능한 기능은 근거 있는 제한을 반환해야 한다.

실패한 기능 때문에 독립적인 기능까지 불필요하게 차단하면 실패다.

### V7. 데이터와 권한 경계 — VR7

진단과 상태 조회 시 원격 Invocation 변경 및 불필요한 외부 효과가 발생하지 않는지 확인한다.

기존 인증 정보와 로컬 기록의 보호 속성이 유지되어야 한다.

사용자 인증 자동화, 봇 체크 우회, 불확실한 원격 상태의 임의 수정, 기존 Service 또는 Job의 무단 중단이 발생하면 실패다.

### V8. 실제 환경 검증의 한계 처리

대표적인 브라우저·Notion 통합 경로는 접근 가능한 실제 외부 환경에서 검증한다.

실제 인증 또는 외부 서비스 이용이 불가능한 환경에서는 통합 테스트와 제어된 실패 재현으로 가능한 부분을 검증하되, 다음을 명시한다.

- 실제로 확인한 동작.
- 외부 환경 부재로 확인하지 못한 동작.
- 이를 보완하는 가장 가까운 검증 근거.
- 남아 있는 불확실성.

필요한 관찰 지점이나 테스트 수단이 부족하고 이번 범위에서 보완할 수 있다면 해당 검증 능력까지 마련한다.

## Verification Tools

- **CLI 명령 및 종료 결과**: 실제 진단·제출·조회 행동과 출력 계약 확인.
- **Service 및 Browser Broker 테스트**: 실행 효과, 프로필 소유권, 컨텍스트 정리, 오류 전파 확인.
- **`attempts` 및 복구 조회 인터페이스**: 로컬 증거, Attempt 식별자, 판단 결과 확인.
- **실제 Notion Invocation 조회**: 원격 접수, 상태, 중복 생성 여부에 대한 권위 있는 확인.
- **격리된 브라우저·XDG 테스트 환경**: 무단 브라우저 실행, 기존 사용자 상태 침범, 기능 부족 상황 검증.
- **실제 수동 인증 및 제출 흐름**: 허가된 환경에서 사용자 개입과 정상 실행의 연결 확인.
- **CLI 및 HTTP 계약 테스트**: 구조화된 오류, 호환성, 접근 권한과 의미 일치 여부 확인.
