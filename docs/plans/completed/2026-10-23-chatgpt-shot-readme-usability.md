# 2026-10-23-chatgpt-shot-readme-usability

## Objective

`chatgpt-shot`의 README를 처음 접하는 사람이 도구의 효용과 사용 상황을 즉시 이해하고, 정상적인 사용 흐름을 쉽게 따라 할 수 있는 문서로 개선한다.

사람에게는 직관적이고 시각적으로 정돈된 사용 안내를, 에이전트에게는 실행 능력과 권한에 맞는 정확한 사용·실패 처리 지침을 제공한다.

README는 기술적 정확성을 유지하면서도 도구의 가치가 첫 화면에서 드러나는 제품 소개이자 실용적인 사용 설명서가 되어야 한다.

## Intent

현재 README에는 설치, 설정, 비동기 Job 계약, 로컬 진단, 오류 처리, HTTP 인터페이스 등 중요한 정보가 충분히 존재한다. 그러나 내부 동작과 상세 계약의 비중이 커서 도구의 효용 및 일상적인 사용 방법을 빠르게 파악하기 어렵다.

특히 다음 불편함을 개선하려 한다.

- 도구가 무엇을 해결하고 언제 유용한지 첫 화면에서 직관적으로 이해하기 어렵다.
- 최초 설정, 정상 사용, 진단, 복구, 내부 명세가 혼재되어 핵심 사용 흐름이 잘 드러나지 않는다.
- 에이전트가 README를 읽더라도 실패 후 어떤 행동이 적절한지 일관되게 판단하기 어렵다.
- `open`, `doctor`처럼 실행 효과가 다른 명령을 정상 사용 또는 일반적인 복구 단계로 오인할 수 있다.
- 문서의 정보량과 별개로 시각적 위계와 전체적인 디자인 완성도를 개선할 여지가 있다.

README의 앞부분은 효용과 사용 경험을 중심으로, 뒷부분은 상세 정보와 에이전트 사용 지침을 중심으로 구성한다.

문서 개선은 실제 실행 동작 개선과 별개의 목표다. 현재 구현이 제공하지 않는 능력을 문서만으로 보장하지 않는다.

## Verification Requirements

**VR1. 효용의 즉시 전달**

- README의 첫 화면에서 `chatgpt-shot`의 목적, 주요 이점, 일반적인 사용 상황을 이해할 수 있어야 한다.
- ChatGPT Web에 프롬프트를 제출하고 Notion Invocation Job을 통해 접수 및 결과를 조회하는 핵심 흐름이 명확해야 한다.
- 도구가 제공하는 효용과 제공하지 않는 보장을 혼동시키지 않아야 한다.

**VR2. 정상 사용 흐름의 접근성**

- 설치 및 최초 설정부터 작업 제출과 결과 조회까지 사용자가 자연스럽게 따라갈 수 있어야 한다.
- 정상적인 사용에 필요한 명령과 예제가 문서에서 우선적으로 드러나야 한다.
- 최초 인증 등 사용자 개입이 필요한 작업은 일반적인 자동 실행 흐름과 구분되어야 한다.
- 제출 접수와 원격 작업 완료의 차이가 명확해야 한다.

**VR3. 실패 처리 안내의 정확성**

- 주요 제출 실패와 원격 Job 실패를 구별할 수 있어야 한다.
- 재제출이 안전한 경우, 불확실한 경우, 사용자 개입이 필요한 경우의 차이가 명시되어야 한다.
- 진단 명령의 실제 실행 효과와 제약이 정확하게 설명되어야 한다.
- 에이전트가 문서의 예제를 단순히 순서대로 실행하는 것만으로 불필요한 가시적 브라우저 실행이나 중복 제출을 유발하도록 안내하지 않아야 한다.

**VR4. 에이전트 사용 지침의 독립성**

- README 하단에 사람이 읽는 일반 사용 안내와 구별되는 에이전트용 섹션이 있어야 한다.
- 에이전트가 지원되는 명령, 정상 흐름, 실패 처리, 재제출 제한, 사용자 개입 조건을 파악할 수 있어야 한다.
- 에이전트의 실행 능력과 권한 차이에 따라 가능한 작업과 불가능한 작업을 구별하도록 안내해야 한다.
- 기능이 없거나 권한이 부족한 환경에서 무리하게 복구를 시도하도록 유도하지 않아야 한다.

**VR5. 문서의 가독성 및 시각적 완성도**

- README의 시각적 위계가 명확하고 핵심 내용을 훑어보기 쉬워야 한다.
- 효용 설명, 사용 예제, 명령 참조, 기술 명세가 서로 구별되어야 한다.
- 코드 예제, 표, 흐름 표현, 여백, 제목 구조를 일관되게 사용해야 한다.
- 장식적인 요소가 정보 전달을 방해하거나 실제 기능을 과장해서는 안 된다.
- 자세한 내용을 원하는 사용자가 기술 계약과 진단 정보를 빠짐없이 찾을 수 있어야 한다.

**VR6. 실제 동작과의 일치 및 범위 보존**

- README의 명령, 옵션, 출력, 실패 의미는 해당 시점의 실제 구현과 일치해야 한다.
- 기존의 중요한 사용 계약과 기술 정보가 문서 개편 과정에서 누락되거나 왜곡되지 않아야 한다.
- 이번 작업은 문서 개선으로 한정하며 CLI, Service, Broker, Notion Invocation의 동작을 변경하지 않아야 한다.

## Definitions

- **README 첫 화면**: GitHub에서 README를 열었을 때 긴 탐색이나 스크롤 없이 먼저 접하는 도입부.
- **정상 사용 흐름**: 준비된 환경에서 프롬프트를 제출하고 반환된 Job ID로 원격 작업을 조회하는 일반적인 경로.
- **접수(Acceptance)**: 원격 Invocation이 `in_progress`, `completed`, `failed` 중 하나로 관찰되어 제출 접수가 확인된 상태.
- **완료(Completion)**: 원격 Invocation이 `completed` 또는 `failed`의 최종 상태에 도달한 것.
- **사용자 개입**: 인증, 브라우저 확인, 권한 승인 등 자동 실행이 임의로 대체해서는 안 되는 사용자 행동.
- **에이전트 사용 지침**: 도구를 호출하는 외부 에이전트에게 적용되는 명령 선택, 실패 처리 및 개입 경계.
- **실행 능력(Capability)**: 현재 환경에서 CLI 실행, 로컬 기록 조회, Notion 접근, 브라우저 실행 또는 대화형 사용자 개입이 가능한지에 관한 조건.
- **실행 권한(Authorization)**: 기술적으로 가능한 행동에 대해 사용자나 상위 실행 주체가 실제로 허용한 범위.

## Decisions

### D1. README의 첫 화면은 효용을 전달한다

문서 상단에는 다음 정보가 드러나도록 한다.

- 도구를 설명하는 짧고 명확한 소개.
- 사용자가 얻게 되는 구체적인 이점.
- `submit → Job ID → jobs → Result`의 핵심 흐름.
- 실제 CLI를 사용하는 간결한 예제.

설치 세부 사항이나 내부 구현 설명보다 제품의 목적과 사용 경험을 먼저 제시한다.

효용을 보여주는 흐름도 또는 간단한 시각적 표현을 사용할 수 있지만, 별도의 복잡한 디자인 시스템이나 이미지 자산을 필수로 만들지 않는다.

### D2. 사용 흐름과 상세 참조를 분리한다

README는 다음 순서를 기본으로 구성한다.

1. 제품 소개와 효용.
2. 핵심 동작 흐름.
3. Quick Start 및 최초 설정.
4. 일상적인 제출과 결과 조회.
5. 실패 처리와 Troubleshooting.
6. 명령 및 기술 참조.
7. 에이전트 사용 지침.

상세 HTTP 계약, 진단 이벤트, 내부 동작 설명 등은 필요에 따라 `docs/` 아래의 참조 문서로 분리한다.

이 경우 README에서 해당 문서로 자연스럽게 이동할 수 있어야 하며, 동일한 규약을 여러 위치에 중복 유지하지 않는다.

### D3. 최초 설정과 일상적 사용을 구별한다

- `open`은 사용자 인증 또는 수동 확인을 위한 명령으로 소개한다.
- 현재 `doctor`는 실제 브라우저 준비 상태를 확인하는 능동 진단이라는 점을 명시한다.
- `submit`과 `jobs`를 일상적인 핵심 명령으로 소개한다.
- `attempts`는 실패 조사에 사용되는 로컬 기록 조회 명령으로 소개한다.
- `npm run smoke`는 실제 외부 제출을 수행하며 사용자 인증이 필요하면 브라우저를 열 수 있는 검증 작업으로 소개한다.

초기 설정 예제가 일반적인 자동 복구 절차로 해석되지 않도록 구성한다.

### D4. 에이전트 지침은 README 하단에 배치한다

일반 사용 안내를 먼저 마무리한 뒤 독립된 `For coding agents` 섹션을 제공한다.

해당 섹션은 다음 규칙을 중심으로 간결하게 구성한다.

- 정상 제출과 Job 조회 흐름.
- 실패 후 기존 실행 기록을 우선 확인하는 원칙.
- 불확실한 제출의 자동 재시도 금지.
- 사용자 승인 없는 가시적 브라우저 실행 금지.
- 환경에서 사용할 수 있는 능력과 사용자 권한을 구별.
- 복구할 수 없는 문제의 명확한 보고.

저장소의 `AGENTS.md`는 개발·유지보수 에이전트를 위한 기존 지침으로 유지한다. README의 에이전트 섹션은 도구를 사용하는 외부 에이전트를 대상으로 한다.

### D5. 현재 기능만 현재형으로 설명한다

실행 동작 개선 계획에서 제안한 새로운 진단 인터페이스나 복구 동작은 실제 구현 전까지 현재 기능으로 설명하지 않는다.

기능 개선 이후 README와 관련 참조 문서를 갱신할 책임은 별도의 실행·복구 개선 계획에 둔다.

### D6. 보호 범위 및 명명

- CLI 명령과 출력 계약, Service, Browser Broker, Notion Invocation 프로토콜, 설정 경로와 데이터 처리를 변경하지 않는다.
- 기존 진단·복구 계약을 문서 편집만으로 재정의하지 않는다.
- 문서 파일명과 주요 제목은 실제 역할을 드러내야 하며, 임시 작업 맥락이나 불필요한 미래 추상화를 기준으로 명명하지 않는다.

## Planned Units

### U1. 제품 소개 및 핵심 사용 경험

README의 첫 화면, 핵심 효용, 기본 흐름, Quick Start, 일상적인 사용 예제를 제공한다.

결과물은 별도의 내부 구현 이해 없이도 도구의 가치와 기본 사용법을 파악할 수 있는 문서다.

### U2. 실패 안내 및 기술 참조

실패 유형, 진단 명령, 최초 인증과 사용자 개입, 원격 Job 상태를 이해하기 쉽게 정리한다.

상세 기술 정보는 필요한 깊이에서 참조할 수 있도록 구성한다.

### U3. 에이전트 사용 지침 및 문서 표현

README 하단의 에이전트 지침을 작성하고, 문서 전체의 시각적 위계와 표현을 정돈한다.

에이전트 지침과 일반 안내가 서로 모순되지 않도록 한다.

## Verification

### V1. 첫 화면의 효용 전달 — VR1

README의 실제 GitHub 렌더링 결과를 확인한다.

도구에 익숙하지 않은 독자의 관점에서 도입부만 보고 다음을 설명할 수 있는지 평가한다.

- 무엇을 하는 도구인가?
- 어떤 상황에 유용한가?
- 가장 기본적인 사용 방식은 무엇인가?
- 실행하면 어떤 결과를 얻는가?

핵심 정보를 찾기 위해 상세 구현 설명을 먼저 읽어야 한다면 실패다.

### V2. 정상 사용 안내 — VR2

README의 설치·설정·제출·조회 예제를 실제 CLI 도움말 및 구현과 대조한다.

실행 가능한 환경에서는 대표적인 제출과 Job 조회 흐름을 확인한다.

제출 접수와 최종 완료를 혼동하거나, 처음부터 불필요한 진단·복구 명령을 수행하도록 안내하면 실패다.

### V3. 실패 안내 — VR3

인증 필요, 사용자 개입, Service 사용 중, 원격 수락 지연, 제출 불확실성, 브라우저 정리 실패의 대표 사례에 README 안내를 적용한다.

각 사례에서 문서의 지침만으로 안전한 다음 행동 또는 중단 사유를 결정할 수 있어야 한다.

자동 재제출이나 예상하지 못한 브라우저 실행을 유도하면 실패다.

### V4. 에이전트 지침 — VR4

다음 환경을 가정하여 문서의 실행 규칙을 점검한다.

- 모든 필수 기능을 사용할 수 있는 환경.
- 로컬 진단만 가능한 환경.
- Notion 조회는 가능하지만 브라우저 실행은 불가능한 환경.
- 브라우저 기능은 있으나 사용자 인증이 필요한 환경.
- 기술적 실행 능력은 있지만 사용자 권한이 없는 환경.

문서에 없는 기능을 가정하거나 지원되지 않는 복구를 시도하도록 안내하면 실패다.

### V5. 디자인 및 정보 접근성 — VR5

GitHub Markdown 렌더링에서 제목, 코드 블록, 표, 링크, 간격, 탐색 흐름을 확인한다.

일반적인 화면 너비에서 핵심 정보가 읽히고 기술 명세가 주요 사용 흐름을 압도하지 않아야 한다.

분리한 참조 문서의 링크가 유효하고 정보가 누락되지 않아야 한다.

### V6. 동작 일치 및 변경 범위 — VR6

README와 변경된 문서에 기재된 명령 및 동작을 실제 코드와 비교한다.

문서 개편으로 실행 파일이나 런타임 계약이 변경되지 않았음을 확인한다.

외부 검증 환경이 없어 실제 제출을 재현할 수 없다면 구현·테스트 및 기존 실증 자료로 확인한 범위를 명시하고, 확인하지 못한 외부 동작은 검증 완료로 취급하지 않는다.

## Verification Tools

- **GitHub Markdown 렌더링**: 실제 README의 시각적 구성과 탐색성 확인.
- **CLI `--help` 및 관련 구현**: 명령, 옵션, 출력, 실행 효과의 일치 여부 확인.
- **기존 테스트**: 문서가 설명하는 주요 계약의 구현 근거 확인.
- **실제 `submit` 및 `jobs`**: 허가된 환경에서 정상 사용 경로와 원격 Job 조회 확인.
- **`attempts` 및 기존 진단 기록**: 실패 안내에 필요한 증거와 실제 조회 가능 정보 확인.
- **Markdown 링크 및 문서 구조 검사**: 분리된 참조 정보의 접근성과 누락 여부 확인.
