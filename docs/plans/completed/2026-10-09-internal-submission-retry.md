# 2026-10-09-internal-submission-retry

## Objective

chatgpt-shot이 최초 제출 후 90초까지 원격 수락을 확인하지 못하면 내부적으로 한 번 재제출하여, 기존 180초 제출 제한 내에서 Job 수락 가능성을 높인다.

## Intent

현재 chatgpt-shot은 제출 여부가 불확실할 때 중복 실행 가능성을 피하기 위해 재시도를 제한한다.

그러나 최근 100건의 실행 로그를 검토한 사용자 판단에 따르면, 재시도로 실제 중복 제출이 발생할 가능성이 있는 사례는 약 2건이었으며, 실제 제출이 이루어지지 않은 채 타임아웃되는 사례가 훨씬 많았다.

chatgpt-shot을 통한 작업은 주로 프롬프트를 전달하고 출력을 생성하는 것이므로, 사용자는 제한적인 중복 실행 위험보다 제출 실패를 줄이는 것을 우선한다.

따라서 원격 수락을 확인하지 못한 제출은 실패한 시도로 간주하고 적극적으로 재시도한다. `pending` 상태이거나 전달 여부가 불확실하더라도 재시도를 제한하지 않는다.

외부에 노출되는 비동기 Job 계약과 180초 제출 제한은 유지한다.

## Verification Requirements

### 1. 내부 재제출

- 최초 프롬프트 입력 시작 후 90초까지 원격 수락이 확인되지 않으면 내부적으로 한 번 재제출한다.
- 마지막으로 관찰된 Notion State가 `pending`이어도 재시도한다.
- 최초 제출의 전달 여부가 `submitted` 또는 `uncertain`이어도 원격 수락이 확인되지 않았다면 재시도한다.
- Notion 조회 실패나 응답 지연으로 원격 수락 여부가 불확실해도 재시도 대상에 포함한다.
- 재시도 전에 원격 수락이 확인되었거나 호출이 취소되었다면 재시도하지 않는다.
- 실제 프롬프트 전송 시도는 최초 제출을 포함해 최대 2회다.
- 재시도가 원격 작업의 중복 실행을 유발할 가능성은 허용한다.

### 2. 전체 제출 제한

- 외부에 노출되는 전체 제출 제한의 기본값은 기존과 동일한 180초다.
- 전체 제출 제한은 최초 프롬프트 입력 시작 시점부터 계산한다.
- 내부 재시도로 인해 전체 제출 제한이 초기화되거나 연장되지 않는다.
- 기존 `CHATGPT_SHOT_ACKNOWLEDGEMENT_TIMEOUT_MS` 설정은 전체 제출 제한으로 유지한다.
- 설정된 전체 제출 제한이 90초 이하라면 내부 재시도를 시작하지 않는다.
- 전체 제출 제한까지 원격 수락이 확인되지 않으면 기존 제출 오류 계약에 따라 종료한다.

### 3. Job 및 원격 수락 계약

- 최초 제출과 내부 재시도는 동일한 Job ID와 Notion Invocation을 사용한다.
- 재시도를 위해 새로운 Invocation을 생성하지 않는다.
- 원격 수락의 판단 기준은 기존과 동일하게 Notion의 `in_progress`, `completed`, `failed` 상태다.
- `pending`은 원격 수락으로 인정하지 않는다.
- 원격 수락이 확인되면 추가 제출 없이 해당 Job ID를 반환한다.
- 성공 응답은 기존과 동일하게 제출 브라우저 탭의 종료가 확인된 후 반환한다.
- CLI 및 HTTP API의 성공 응답 형식은 변경하지 않는다.
- 수락 이후 Result, Error 및 terminal 상태 관찰은 기존 Job 계약을 유지한다.

### 4. 실패 및 경합 처리

- 동일 Job의 실제 프롬프트 전송 시도는 최대 2회로 제한하며, 이전 브라우저 전송 작업과 재시도가 충돌해 추가 전송이 발생하지 않아야 한다.
- 재시도 전후 원격 수락이 확인되면 추가 전송보다 수락 처리를 우선한다.
- 재시도 전송이 실패해도 최초 제출이 실패했다고 단정하지 않으며, 남은 전체 제출 제한 동안 원격 수락 확인을 계속한다.
- 최초 제출 또는 재시도가 원격 실행을 시작했을 가능성이 있다면, 원격 수락이 확인되지 않았다는 이유만으로 Invocation을 삭제하거나 State 및 Error를 덮어쓰지 않는다.
- 기존의 확실한 미전송 실패에 대한 정리 동작은 유지한다.
- 취소, 브라우저 오류, Notion 조회 오류, 전체 제출 제한 및 브라우저 탭 종료 실패에 대한 기존 오류 계약의 의미를 유지한다.
- 내부 재시도의 성공이나 실패는 별도 Job으로 노출되지 않는다.

### 5. 실행 로그

- 기존 로컬 실행 로그에서 최초 제출과 내부 재시도를 구분할 수 있어야 한다.
- 동일한 Job ID로 재시도 발생 시점, 사유, 전송 결과 및 최종 수락 여부를 추적할 수 있어야 한다.
- 기존 로그의 저장 위치, 보존 범위 및 민감정보 제외 정책을 유지한다.
- 로그 기록 실패가 제출 결과를 변경하지 않아야 한다.

## Definitions

- **Job**: chatgpt-shot Service가 발급하는 UUID로 식별하는 비동기 작업.
- **Invocation**: Job에 대응하는 Notion의 영속 기록.
- **제출 시도**: ChatGPT에 프롬프트를 전달하기 위한 브라우저 전송 시도.
- **내부 재시도**: 기존 Job과 Invocation을 유지하면서 프롬프트 전송을 다시 시도하는 행위.
- **원격 수락**: Invocation의 Notion State가 `in_progress`, `completed`, `failed` 중 하나로 관찰된 상태.
- **전체 제출 제한**: 최초 프롬프트 입력 시작부터 원격 수락을 기다리는 최대 시간. 기본값은 180초.
- **재시도 시점**: 최초 프롬프트 입력 시작 후 90초가 경과한 시점.
- **중복 실행**: 최초 제출과 내부 재시도가 모두 ChatGPT에 전달되어 동일 작업이 두 번 실행되는 상황. 별도의 Job이 생성된다는 의미는 아니다.

## Decisions

### 1. 재시도 정책

- 기본 재시도 시점은 90초로 고정한다.
- 최초 제출을 포함해 최대 2회의 전송 시도만 허용한다.
- 별도의 재시도 시점이나 횟수 설정은 추가하지 않는다.
- 원격 수락이 확인되지 않았다는 사실만으로 재시도를 결정할 수 있으며, 최초 제출의 미전송 증거를 요구하지 않는다.
- 재시도는 기존 Job 제출 흐름 내부에서 수행한다.
- 동일한 Invocation을 참조하는 프롬프트를 재전송한다.
- 재시도에 필요한 브라우저 상태 준비는 기존 브라우저 책임 경계에서 수행한다.

### 2. 원격 수락과 중복 실행

- Notion State를 원격 수락의 권위 있는 근거로 유지한다.
- 브라우저 전송 결과나 UI 증거만으로 원격 수락을 확정하지 않는다.
- 원격 수락이 늦게 반영되어 동일 프롬프트가 두 번 전달되는 상황을 허용한다.
- 중복 실행 가능성을 이유로 새로운 Job이나 Invocation을 생성하지 않는다.
- 중복 실행 허용과 Invocation 삭제 안전성은 별개로 판단한다.

### 3. 기존 계약 보호 범위

다음 영역은 이번 변경에서 유지한다.

- CLI `submit`, `jobs` 및 Service HTTP Job API
- Service 인증 및 Job UUID 생성
- Notion Invocation 스키마와 원격 State 소유권
- 전체 제출 제한 및 사용자 설정 방식
- 원격 수락 이후 브라우저 탭 종료와 terminal 관찰
- Service 시작, 종료, 수동 브라우저 열기 및 인증 흐름
- 기존 제출 오류 코드의 의미
- 로컬 실행 로그의 저장 위치, 보존 범위 및 민감정보 보호 정책

이 범위를 넘는 변경은 별도 계획으로 분리한다.

### 4. 책임 및 명명

- 내부 재시도 판단과 전체 제출 제한 관리는 기존 Job 제출 책임 안에 둔다.
- 브라우저 조작과 Notion 상태 관찰의 기존 책임 경계를 유지한다.
- 파일, 모듈, 타입 및 주요 함수명은 현재 책임과 역할을 드러내도록 한다.
- 실제로 존재하지 않는 확장 구조를 가정한 추상화는 추가하지 않는다.

## Planned Units

### 1. 내부 재제출 및 Job 계약 유지

90초까지 원격 수락이 확인되지 않은 Job에 대해 기존 Invocation을 사용하여 한 번 재제출한다.

`pending`, `submitted`, `uncertain` 및 Notion 관찰 실패 상황에서도 의도한 재시도 정책이 적용되도록 한다.

최대 전송 횟수, 전체 제출 제한, 원격 수락 우선 처리와 기존 실패·정리 계약을 함께 유지한다.

완료 기준:

- 원격 수락이 확인되지 않으면 90초에 내부 재시도가 발생한다.
- 원격 수락이 확인된 Job은 재시도하지 않는다.
- 동일 Job과 Invocation을 유지하며 전송 시도는 최대 2회다.
- 전체 제출 제한은 연장되지 않는다.
- 실패, 취소 및 전송 경합에서 기존 Job과 Invocation의 의미가 유지된다.

### 2. 재시도 관측 및 계약 문서화

기존 로컬 실행 로그에서 내부 재시도를 구분할 수 있도록 하고 README에 변경된 정책을 반영한다.

재시도 조건과 중복 실행 가능성을 문서화하고, 기존 제출 계약의 회귀 여부를 검증한다.

완료 기준:

- Job 로그에서 최초 제출과 재시도 및 최종 결과를 구분할 수 있다.
- README가 90초 내부 재시도와 180초 전체 제출 제한을 정확하게 설명한다.
- 기존 테스트, 빌드 및 production smoke 검증이 통과한다.

## Verification

### 1. 내부 재시도 동작

제어 가능한 시간과 상태를 사용하는 테스트로 다음 상황을 검증한다.

- 90초 이전 원격 수락: 전송 1회
- 90초까지 `pending` 유지: 전송 2회
- 최초 전달 상태 `submitted`, 원격 수락 없음: 전송 2회
- 최초 전달 상태 `uncertain`, 원격 수락 없음: 전송 2회
- Notion 조회 실패 또는 지연으로 수락 확인 불가: 재시도 대상
- 재시도 직전 수락 확인: 추가 전송 없음
- 재시도 이전 호출 취소: 추가 전송 없음
- 전체 제출 제한 90초 이하: 추가 전송 없음

전송 시도 횟수, 시점 및 원격 수락 관찰 결과가 요구사항과 일치하면 통과한다.

### 2. 전체 제출 제한 및 Job 일관성

재시도가 발생하는 테스트에서 다음을 확인한다.

- 전체 제출 제한이 최초 프롬프트 입력 시점부터 유지된다.
- 재시도 이후 전체 제출 제한이 초기화되지 않는다.
- 동일한 Job ID와 Invocation을 사용한다.
- 추가 Invocation이 생성되지 않는다.
- 원격 수락 시 기존 형식의 Job UUID 하나만 반환한다.
- 최대 2회의 전송 시도를 초과하지 않는다.

시간 기록, 브라우저 전송 횟수, Invocation 생성 기록 및 제출 응답을 증거로 사용한다.

### 3. 실패 및 경합 처리

대표적인 실패 상황을 제어 가능한 테스트로 검증한다.

- 최초 제출의 원격 수락이 늦게 관찰되는 경우
- 재시도 실패 후 최초 제출의 수락이 관찰되는 경우
- 재시도 도중 원격 수락이 관찰되는 경우
- 최초 브라우저 전송 작업이 완료되지 않은 상태에서 재시도 시점에 도달하는 경우
- Notion 조회가 완료되지 않거나 오류를 반환하는 경우
- 재시도 이전 또는 도중 호출이 취소되는 경우
- 전체 제출 제한까지 수락이 확인되지 않는 경우
- 원격 수락 후 브라우저 탭 종료가 실패하는 경우

전송 횟수, 반환 결과, Invocation 보존 및 정리 여부, 오류 코드와 로그를 확인한다.

추가 전송이 2회를 초과하거나, Invocation이 잘못 삭제되거나, 전체 제출 제한이 연장되거나, 기존 오류 계약이 변경되면 실패로 판단한다.

### 4. Production smoke

기존 `npm run smoke`를 사용해 실제 production CLI → Service → Browser → ChatGPT → Notion 경로에서 정상 제출을 수행한다.

다음을 확인한다.

- CLI가 기존 형식의 Job UUID를 반환한다.
- 해당 Job을 `chatgpt-shot jobs <uuid>`로 조회할 수 있다.
- Notion Invocation의 원격 수락 및 최종 상태를 확인할 수 있다.
- 로컬 실행 로그에서 제출과 수락 흐름을 확인할 수 있다.

이 검증은 내부 재시도의 실제 발생을 입증하기 위한 것이 아니라, 변경으로 기존 외부 제출 경로가 깨지지 않았음을 확인하기 위한 것이다.

실제 환경에서 인위적인 90초 지연을 유발하는 E2E 검증은 수행하지 않는다.

90초 재시도 정책과 경합 동작은 앞선 제어 가능한 테스트로 검증한다.

### 5. 전체 회귀 확인

`npm test`와 `npm run build`를 실행한다.

기존 정상 제출, 인증, Notion 승인 복구, 오류 처리, Job 조회 및 로컬 실행 로그 관련 테스트가 모두 통과해야 한다.

## Verification Tools

- `npm test`: 재시도 조건, 최대 전송 횟수, 전체 제출 제한, 원격 수락, 실패 및 경합 검증.
- `npm run build`: TypeScript 빌드 및 타입 계약 확인.
- `npm run smoke`: 실제 production 제출 경로와 기존 외부 계약 확인.
- `chatgpt-shot jobs <uuid>`: 영속 Job의 상태, 결과 및 오류 조회.
- `chatgpt-shot attempts <uuid>`: 최초 제출, 내부 재시도, 실행 시간 및 최종 수락 흐름 확인.
- Notion Invocation 조회: 원격 State와 Invocation 일관성 확인.
