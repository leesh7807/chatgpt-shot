# 2026-10-27-in-progress-app-approval-assist

## Objective

`chatgpt-shot`의 기존 앱 승인 보조가 허용 버튼을 판별할 때 버튼 기준 상위 3단계 조상 요소까지 승인 카드 문맥을 조사하도록 확장한다. 또한 Notion Invocation의 `pending`뿐 아니라 `in_progress` 중에도 해당 ChatGPT 대화에 나타나는 지원 대상 앱의 허용 버튼을 자동으로 누를 수 있게 한다.

이 기능은 `chatgpt-shot`의 핵심 제출·Job 생명주기와 분리되어, 필요 없어지면 독립적으로 제거하거나 비활성화할 수 있는 보조 모듈로 유지한다.

## Intent

현재 승인 보조는 허용 버튼 자체와 상위 2단계 조상 요소까지만 앱 문맥을 검사한다. 버튼과 앱 이름이 더 멀리 떨어진 카드 구조에서는 탐지가 누락될 수 있다.

또한 보조 기능은 `pending` 접수 대기 중에만 호출된다. Invocation이 `in_progress`로 전환되면 `submit`은 접수된 Job을 반환하기 전에 제출 탭을 닫고, 이후에는 Notion 상태만 관찰한다. 따라서 접수된 작업을 처리하는 도중 ChatGPT가 새 앱 승인을 요청해도 현행 보조 기능은 이를 처리하지 못한다.

원하는 변화는 승인 보조의 탐지 범위와 동작 기간을 넓히는 것이지, 앱 승인 자동화를 핵심 워크플로의 영구적인 전제조건으로 만들거나 Notion을 대신해 Job 상태를 판정하는 것이 아니다.

## Verification Requirements

VR1. 승인 카드 문맥 탐지의 확대와 정확성

- 허용 버튼을 기준으로 부모 요소를 최대 3번 따라 올라가며 지원 대상 앱의 승인 문맥을 인식한다. 기존에 인식하던 더 가까운 문맥도 계속 인식한다.
- 지원 대상은 현재 보조 기능이 다루는 Notion 및 Chrome 승인 카드로 유지한다. 단지 더 높은 공통 조상에 앱 이름이 있다는 이유로 무관한 버튼이나 다른 앱의 승인 버튼을 눌러서는 안 된다.
- 활성·가시 상태와 버튼 종류를 확인하고, 기존 우선순위인 `Always allow` → `Allow once` → 정확한 `Allow`를 유지한다. 대상이 모호하거나 클릭 가능한 허용 버튼을 신뢰할 수 없으면 누르지 않는다.
- 허용 동작은 기존과 같이 신뢰된 브라우저 마우스 입력을 사용한다.

VR2. `pending`과 `in_progress`에서의 승인 처리

- 기존 `pending` 상태의 승인 보조가 계속 동작한다.
- Notion에서 `in_progress`가 처음 관측된 직후부터, `submit`이 Job ID를 반환한 이후까지 해당 Job의 대화에서 발생하는 지원 대상 승인 요청을 관찰하고 처리할 수 있다.
- 동일 Job에서 승인 요청이 반복되어도 관찰과 클릭 시도를 이어갈 수 있으며, `completed` 또는 `failed`가 관측되면 그 Job의 승인 관찰을 끝낸다.
- 지원 대상 승인 카드가 없을 때에는 불필요한 클릭을 하지 않는다.

VR3. 기존 Job 및 제출 계약의 보존

- 원격 접수 판단은 계속 Notion의 `in_progress`, `completed`, `failed` 관측만으로 결정한다. 버튼 탐지·클릭·사라짐은 접수 또는 작업 완료의 증거로 간주하지 않는다.
- `submit`은 접수 확인 및 기존 제출 탭 종료 확인 이후 Job UUID를 반환하는 계약을 유지한다. `in_progress` 승인 감시가 응답 반환을 기다리게 만들지 않는다.
- `jobs`, `inspect`, HTTP 응답, Invocation 상태·Result·Error의 권한과 의미, 제출 실패·취소·불확실성 처리, 자동 재제출 금지는 바뀌지 않는다.
- 승인 보조 자체는 Notion 상태를 기록하거나 ChatGPT 로그인 절차를 자동화하지 않는다.

VR4. 선택적 보조 기능의 독립성과 실패 격리

- 승인 탐지·판별·클릭 및 후속 관찰은 식별 가능한 보조 기능의 책임으로 남아 있어야 한다. 그 기능을 제거하거나 실행하지 않아도 기본 제출, 원격 접수 판정, Job 결과 관찰은 동작해야 한다.
- 승인 카드의 구조 변경, 대화 탭 부재, 브라우저 오류, 시간 초과, 관찰 세션 종료가 Job의 접수·완료 상태나 제출 응답을 바꾸지 않는다. 확인되지 않은 클릭을 성공으로 기록하지 않는다.
- 관찰은 현재 Job의 ChatGPT 대화 및 기존 허용된 앱 승인 범위에만 적용되며, 다른 Job·탭·도구의 권한을 임의로 변경하지 않는다.

VR5. 브라우저 수명과 자원 경계

- `in_progress` 중 승인 처리에 필요한 브라우저 관찰은 반환 전 닫아야 하는 원래 제출 탭과 별도로 유지된다.
- Job이 종료되거나 관찰을 계속할 수 없게 되면 보조 관찰에 사용한 탭·작업·자원이 정리되어야 한다. 관찰 실패 때문에 원래 제출 탭의 종료 확인을 생략하거나 무한정 보류하지 않는다.
- 서비스 중지, 사용자에 의한 브라우저 프로필 열기, 취소 및 동시 Job 처리와 기존의 소유권·격리 경계를 충돌시키지 않는다. 이 경우 승인 관찰을 중단할 수 있지만 원격 Job 관찰의 정확성은 유지한다.

VR6. 실제 결과와 검토 가능한 증거

- 버튼 기준 세 번째 조상에서만 지원 대상 앱 문맥을 찾을 수 있는 사례와, 그 확대 때문에 잘못 클릭할 수 있는 사례를 구별할 수 있어야 한다.
- `pending` 처리, 접수 이후 `in_progress` 처리, 터미널 상태 종료, 보조 기능 부재·실패, 동시 Job 격리의 대표 경로가 관찰 가능해야 한다.
- 실제 ChatGPT 브라우저에서 승인 카드와 입력 결과를 코드·테스트만으로 충분히 판단할 수 없다면, 전달된 구현에 대응하는 대표 직접 증거를 개인정보와 비밀을 제외한 형태로 저장소에 보존한다. 실제 승인 카드 재현이 불가능하면 그 사실과 미검증 범위를 명시하고 해당 동작을 실증 완료로 보고하지 않는다.

## Definitions

- 앱 승인 보조(App Approval Assist): 특정 ChatGPT 대화의 지원 대상 앱 승인 카드를 찾아 허용 입력을 시도하는 분리 가능한 기능.
- 조상 단계: 허용 버튼 자신이 0단계, 직접 부모가 1단계, 그 부모가 2단계, 다시 그 부모가 3단계다. 여기서 3단계는 탭 수가 아니라 DOM 부모 탐색 깊이를 뜻한다.
- 승인 카드: 특정 앱의 도구 사용 요청과 그 요청에 속한 허용·거부 조작이 하나의 UI 단위로 연결된 영역.
- 승인 문맥: 후보 허용 버튼이 속한 승인 카드의 대상 앱과 요청을 식별할 수 있는 정보. 같은 페이지 또는 넓은 공통 조상에 앱 이름이 존재한다는 사실만으로 성립하지 않는다.
- 승인 시도: 확인한 카드의 허용 버튼에 브라우저 입력을 보낸 행위. UI의 버튼 소멸, 실제 앱 권한 부여, Notion 접수·완료와는 별개다.
- 원격 접수(Remote Acceptance): Notion Invocation이 `in_progress`, `completed`, `failed` 중 하나로 확인된 상태.
- 제출 탭: 프롬프트 전송에 사용하며 원격 접수 뒤 UUID 반환 전에 닫는 Job별 브라우저 탭.
- 대화 식별 정보: 해당 Job의 ChatGPT 대화에 다시 접근하기 위해 제출 과정에서 확인한, 다른 대화와 혼동되지 않는 위치 정보.
- 승인 관찰 세션: 제출 탭을 소유하지 않으며 원격 접수 후 해당 Job의 대화를 관찰하는 독립적인 보조 브라우저 세션.
- 관찰 관리자: Job별 승인 관찰 세션의 시작·중단·정리와 원격 Job 상태에 따른 수명을 연결하는 Service 내부 책임. 승인 카드 판별이나 원격 Job 상태 기록을 소유하지 않는다.
- 터미널 상태: Notion Invocation의 `completed` 또는 `failed`.

## Decisions

### 승인 카드 식별과 브라우저 입력의 경계

- `src/app-approval-assist.ts`가 지원 앱의 승인 카드 식별, 허용 버튼 선택, 클릭 시도와 결과 해석을 담당한다. 조상 문맥 탐색은 버튼 0단계부터 3단계까지로 확장한다.
- 조상 영역의 텍스트에 `Notion`이나 `Chrome`이 포함된다는 사실만으로 후보 버튼을 선택하지 않는다. 버튼과 요청 정보가 같은 승인 카드에 속한다는 구조적 근거를 확인해야 한다. 형제 카드, 상위 대화 컨테이너 등에서 흘러온 문맥은 대상 근거가 아니다. 구조적 연관성을 판별할 수 없으면 입력하지 않는다. 특정 DOM/CSS 구조에 불필요하게 종속되는 선택은 실행에 맡긴다.
- 지원 앱은 Notion과 Chrome만 유지한다. `Always allow` → `Allow once` → 정확한 `Allow`의 기존 우선순위, 활성·가시 상태 확인, 신뢰된 클릭 및 클릭 결과의 불확실성 구분을 보존한다. 다른 앱이나 일반적인 웹 페이지 버튼으로 범위를 넓히지 않는다.
- `src/broker.ts`는 해당 Job의 제한된 대화 페이지 접근, 신뢰된 마우스 입력, 대상 확인과 탭 정리 등 브라우저 수단을 제공한다. Broker가 Job의 접수·완료를 판정하지 않는다.

### Job 상태와 관찰 세션의 소유권

- `pending` 승인 보조는 기존 제출 경로에서 동작한다. Notion의 `in_progress`를 관측하면 Service의 Job별 관찰 관리자가 별도 승인 관찰 세션의 수명을 맡고, 기존 Job 완료 관찰은 계속 Notion 상태만으로 이루어진다.
- 제출 과정에서 해당 Job의 대화 식별 정보를 확보하되, 원격 접수 후 이를 얻기 위해 추가로 대기하거나 원래 제출 탭의 닫힘·UUID 반환을 지연시키지 않는다. 확보한 식별 정보로만 관찰 세션을 만들며, 유효한 정보가 없다면 그 Job의 접수 이후 승인 관찰은 `unavailable`로 남기고 건너뛴다. 최근 대화나 현재 활성 탭을 임의로 선택하지 않는다.
- 제출 탭은 기존 `withBrowser`/접수 종료 경계에서 닫고, 별도 관찰 세션은 제출 탭의 세션 ID나 생존을 전제로 하지 않는다. 관찰 세션의 시작·작동 실패는 접수 반환에 영향을 주지 않는다. 접수 이후 이미 `completed`/`failed`가 관측된 Job에는 관찰을 시작하지 않는다.
- Job별 관찰 관리자는 기존 완료 관찰에서 확인한 상태를 이용해 `in_progress` 동안 관찰하고 `completed`·`failed` 시 중단한다. 완료 관찰 자체가 오류로 종료된 경우에도 승인 관찰을 정리한다. 승인 보조의 작업이 원격 상태 읽기를 가로막거나, 승인 결과를 원격 상태로 해석하게 해서는 안 된다.
- Job별로 대화·브라우저 세션·관찰 작업을 연결하며, 동시 Job 간 교차 사용과 중복 관찰 루프를 허용하지 않는다. 동일 Job의 반복 승인은 계속 살피되 클릭 보고·화면 변화만으로 처리가 확정되었다고 가정하지 않는다.
- 접수 이후 관찰은 같은 Service 실행 중에 접수된 Job으로 한정한다. Service 재시작 시 기존 `in_progress` Job을 스캔해 재부착하거나 관찰 세션을 영속 복구하는 기능은 이번 범위에 포함하지 않는다. 별도 데몬, 영구 상태 저장소, 새로운 공개 API도 추가하지 않는다.

### 브라우저 소유권과 중단 경계

- 기존 제출 경로의 탭 종료·접수 반환을 우선한다. 원래 제출 탭과 승인 관찰 세션은 각자 정리 책임을 가진다. 관찰을 시작하지 못하거나 정리에 실패하더라도 이를 Job의 원격 실패 또는 제출 실패로 변환하지 않는다. 정리 실패는 별도의 진단 정보로 구별한다.
- 기존 `MAX_APPROVAL_TABS = 3`은 DOM 조상 깊이와 무관한 브라우저 탭 자원 제한이다. 제출 중 보조 경로의 기존 상한은 유지한다. 별도 관찰 세션에도 Job당 동시에 열려 있는 승인 관련 탭을 합산해 최대 3개로 제한하고, 재시도·반복 관찰 때문에 종료된 탭이 누적되거나 무제한으로 새 탭을 남기지 않는다. 특정 탭을 몇 번째 시도에 여는지는 실행 선택으로 남긴다.
- 프로필 소유권이 필요한 `open`/`/prepare-open`, Service 중지, Broker 종료는 승인 관찰보다 우선한다. Service/Broker는 관찰 세션을 식별해 중단·정리한 후 프로필을 넘기거나 닫을 수 있어야 한다. 관찰 세션을 `browserAdmissions`에 합쳐 수동 열기를 무기한 막지 않는다. 실행 중인 승인 클릭이나 읽기도 중단 가능한 유한한 작업으로 취급한다.
- Service 중지가 이미 진행 중인 Job의 Notion 완료 관찰을 다루는 기존 정책은 변경하지 않는다. 다만 승인 관찰은 기존 중지·프로필 양도에 추가적인 완료 대기 조건을 만들지 않는다. 동시에 여러 Job을 처리할 때에도 보조 세션이 다른 Job의 브라우저/프로필 소유권을 대신 점유하거나 종료해서는 안 된다.
- 외부 대화 UI 손실, 관찰 세션 오류, 취소 또는 프로필 양도로 해당 Job의 보조 관찰을 지속할 수 없으면 기록 후 종료한다. 보조 실패를 이유로 새로운 `submit`을 시도하거나 다른 대화를 탐색하지 않는다.

### 분리 가능성과 보호 범위

- `app-approval-assist`의 카드 판별·클릭 책임과 관찰 세션 책임은 명확한 내부 인터페이스로 연결한다. 기본 Service·Browser·Broker 계약에는 승인 보조의 존재를 필수 의존성으로 만들지 않는다. 보조 연결을 호출하지 않거나 해당 모듈을 제거하는 변경만으로 기존 제출과 Notion 완료 관찰을 유지할 수 있어야 한다.
- 비활성화는 내부 연결점에서 보조 기능을 호출하지 않는 상태를 뜻한다. 사용자가 별도 옵션을 요청하지 않았으므로 공개 CLI/HTTP 스위치나 범용 플러그인 프레임워크는 새로 설계하지 않는다.
- 보호 범위: Notion Invocation 스키마와 쓰기 권한, 접수 타임아웃 및 오류 분류, `submit`/`jobs`/`inspect` 계약, 요청 인증, 로그인 절차, 다른 Tool 승인, Notion 기반 원격 Job 완료 관찰, Service 중지·프로필 잠금의 공개 의미. 이 경계를 바꾸는 요구는 별도 계획으로 넘긴다.
- 변경은 승인 보조와 그 연결·소유권을 위해 필요한 최소 Service·Browser·Broker 내부 경계, 관련 테스트와 기술 설명에 한정한다.
- 파일·모듈·타입·주요 함수 이름은 실제 책임을 반영해야 한다. 기존 `recoverPendingAppApproval`처럼 현재 역할을 과도하게 좁히는 이름은 상태 공통 동작에 맞게 정리하되, 아직 존재하지 않는 일반화된 플러그인 체계처럼 미래 역할을 암시하는 이름은 만들지 않는다.

실제 승인 카드의 출현은 외부 UI와 작업 진행에 의존한다. 시험 가능한 범위에서는 승인 보조를 연결한 실제 브라우저/Service 경로를 사용한다. 실제 `in_progress` 카드와 클릭 결과를 확보할 수 없다면 별도 관찰 세션의 실제 브라우저 접근·종료, DOM 재현, Service/Browser/Broker 통합 테스트를 가장 가까운 증거로 제시하되, 그것을 실제 앱 권한 승인 성공과 동일시하지 않는다. 검증에 필요한 브라우저 관찰·상태 읽기 수단이 부족하고 이번 변경 범위에서 마련할 수 있다면 해당 수단을 함께 마련한다.

보존 증거에는 원본 프롬프트, 대화 전문, 인증정보, 비공개 Notion 내용이나 민감한 화면 영역을 포함하지 않는다. 저장소에는 실행 대상 커밋, 관측 상태, 클릭 선택과 결과, 캡처의 출처·한계를 식별할 수 있는 짧은 설명도 함께 둔다.

## Verification Tools

- `npm run build`, `npm test`: 타입·기존 생명주기 회귀 및 탐지·세션 경계의 자동 검증.
- 실제 `chatgpt-shot submit`, `chatgpt-shot jobs <uuid>`, `chatgpt-shot inspect <uuid>`: 사용자 진입점에서 UUID 반환, Notion 권위 상태 및 보조 기능과의 독립성 확인.
- Private Chrome Broker/CDP의 대화 탭 관측, 신뢰된 마우스 입력 및 탭 종료 확인: 실제 카드 식별과 클릭 시도, 브라우저 세션 격리·정리 확인.
- 승인 보조 telemetry 및 `--observe-approval`: Job별 버튼 선택·시도·불확실성, 탭 인덱스, 클릭 전후 화면 증거 확보. 이 기록은 원격 권위 상태를 대체하지 않는다.
- 로컬 격리 실행 또는 `npm run smoke`가 허용되는 환경: 실제 Service/브라우저/Notion 연결의 대표 경로 확인.
- `npm run smoke`의 격리는 XDG Service와 Chrome 프로필 등 로컬 런타임 경계에 한정한다. 복사된 `.env`의 Notion 자격정보·Invocation 데이터베이스와 수동 로그인한 ChatGPT 계정은 실제 외부 계정이므로, 범위와 남는 민감정보를 `VERIFICATION.md`에 명시한다.

## Planned Units

### 1. 지원 대상 승인 카드의 식별과 입력

허용 버튼 자신부터 세 번째 조상까지 조사하되, 버튼과 앱 요청이 하나의 승인 카드에 속하는 경우만 선택한다. 그 외에는 입력하지 않는다. 기존 선택 우선순위와 신뢰된 클릭 경로를 보존한다. DOM 경계·입력 결과는 VR1, VR6에서 검증한다.

### 2. Job별 승인 관찰 수명과 브라우저 소유권

`pending`의 기존 처리에 이어 동일 Service 실행 중 `in_progress` Job의 대화를 별도 세션으로 관찰한다. 대화 식별 정보 인계, 제출 탭과 관찰 세션의 소유권 분리, 터미널·오류·프로필 양도 시 정리를 책임진다. 보조 기능의 비활성화가 기본 Job 흐름에 영향을 주지 않는 것도 이 경계에 포함한다. VR2\~VR6으로 검증한다.
